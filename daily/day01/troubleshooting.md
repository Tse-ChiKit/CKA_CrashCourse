# CKA Day 1 — Troubleshooting Notes

## 1. kubeadm init stuck while pulling images

### Symptom

`kubeadm init` stayed at the image pulling stage for a long time.

### Diagnosis

The container runtime itself was working, but the node could not reliably reach the default Kubernetes image registry. Direct network access also failed, so this was primarily a registry/network reachability problem rather than a kubelet or containerd failure.

### Resolution used in the lab

```bash
sudo kubeadm init \
  --pod-network-cidr=10.244.0.0/16 \
  --image-repository registry.aliyuncs.com/google_containers
```

### Troubleshooting lesson

Separate the problem into layers:

```text
1. Is containerd running?
2. Can the node reach the registry?
3. Can the required image actually be pulled?
4. Is the image reference/tag correct?
```

## 2. kubeadm init later failed around RBAC/admin bootstrap

The initialization got far enough to create control-plane static Pods, but a later admin/RBAC bootstrap step required manual recovery.

The command discussed was:

```bash
sudo KUBECONFIG=/etc/kubernetes/super-admin.conf \
  kubectl create clusterrolebinding kubeadm-cluster-admins \
  --clusterrole=cluster-admin \
  --group=kubeadm:cluster-admins
```

Important lessons:

- `kubeadm-cluster-admins` is the name of the ClusterRoleBinding object.
- `cluster-admin` is the ClusterRole being granted.
- `kubeadm:cluster-admins` is the group receiving that role.
- `KUBECONFIG=...` selects credentials for this `kubectl` command.
- `admin.conf` / `super-admin.conf` are generated by kubeadm; the role-binding command does not create them.

## 3. Why later image problems could still happen after changing the kubeadm repository

A key confusion was whether specifying an alternative repository during `kubeadm init` meant the whole cluster had switched registries.

It had not.

```text
kubeadm --image-repository
    -> applies to kubeadm-managed bootstrap images

DaemonSet image field
    -> applies to Pods created by that DaemonSet

containerd registry/mirror configuration
    -> runtime-level configuration on that node
```

These are separate layers. A worker can therefore still fail to pull another image even though kubeadm initialization succeeded using a mirror.

## 4. kube-proxy / DaemonSet confusion

There is one `kube-proxy` DaemonSet object in cluster state, but it creates separate kube-proxy Pods on eligible nodes.

Updating that DaemonSet affects its own Pod template; it does not globally update unrelated workload image registries.

Useful commands:

```bash
kubectl get ds kube-proxy -n kube-system
kubectl get pods -n kube-system -o wide
kubectl describe pod <pod-name> -n kube-system
```

## 5. kubectl on a worker tried localhost:8080

### Symptom

```text
couldn't get current server API group list
Get "http://localhost:8080/api?...":
dial tcp 127.0.0.1:8080: connect: connection refused
```

### Cause

The worker shell did not have a usable kubeconfig for `kubectl`.

`kubeadm join` configures the kubelet so the worker can join the cluster. It does not automatically configure that user's shell as a cluster administrator.

Preferred lab workflow: run administrative `kubectl` commands from the control-plane node unless there is a deliberate reason to securely configure kubeconfig elsewhere.

## 6. Useful node-level diagnostics

```bash
sudo systemctl status containerd
sudo systemctl status kubelet
sudo crictl images
sudo crictl ps -a
sudo journalctl -u containerd --no-pager -n 100
sudo journalctl -u kubelet --no-pager -n 100
```

## Day 1 troubleshooting hierarchy

```text
kubectl / API object layer
        ↓
controllers / scheduler / kubelet
        ↓
container runtime
        ↓
image registry / network
        ↓
OS / VM networking
```

First identify the failing layer before changing configuration.
